# Relay HTTP API v0 — предварительный контракт

JSON, bearer-capabilities, без аккаунтов. Все идентификаторы и токены —
случайные hex-строки: queue ID и message ID — 16 байт, токены — 32 байта.
Клиент генерирует message ID и повторяет тот же ID при повторной отправке.
На сервере хранятся SHA-256 хеши токенов, но не исходные токены очереди.

| Метод | Путь | Право | Результат |
|---|---|---|---|
| GET | `/health` | Нет | `200` |
| POST | `/v1/queues` | Admin | `201`, ID и два токена |
| POST | `/v1/queues/redeem` | Билет на одну очередь | `201`, только ID |
| POST | `/v1/queues/invite` | Локально выданный билет приглашения | `201`, только ID |
| POST | `/v1/queues/{queue}/messages` | Write | `202` |
| GET | `/v1/queues/{queue}/messages` | Read | До 100 сообщений |
| DELETE | `/v1/queues/{queue}/messages/{message}` | Read | `204`, подтверждение |
| DELETE | `/v1/queues/{queue}` | Read | `204`, удаление |

Заголовок: `Authorization: Bearer <token>`. Read-токен не даёт write-права,
write-токен не даёт read-права. Неверное право и неизвестная очередь возвращают
одинаковый `404`; неверный admin-токен — `401`.

Создание возвращает `{ "id": "...", "write_token": "...", "read_token": "..." }`.
Погашение билета принимает строгий proposal с `id`, `read_token` и
`write_token`, выбранными клиентом; оба токена должны различаться.
Relay сохраняет хеш билета и digest proposal. Точный повтор действующего
билета возвращает ту же очередь; изменённый proposal — `409`, истёкший
билет — `401`. Создание и расходование билета атомарны. Подробный контракт
и операторская команда: [QUEUE_TICKETS.md](QUEUE_TICKETS.md).

`POST /v1/queues/invite` принимает строгий объект `queue` (тот же proposal),
`recipient_ticket` (64 lowercase hex) и `expires_at` (целые Unix-секунды).
Билет приглашения разрешает атомарно создать очередь автора и выдать один
обычный билет получателю. Получатель погашает этот билет через `/redeem`;
делегировать ещё один билет он не может. Срок получателя не превышает срок
исходного билета и 24 часа с момента операции. Ответ содержит только ID
очереди автора. Точный повтор до срока получателя идемпотентен; изменённый
объект даёт `409`. Обычные и ранее выданные билеты не приобретают новые
права: `/invite` возвращает для них `403`. Оператор явно выбирает
`queue_ticket --invite` либо `Store::issue_invitation_ticket`.

В SQLite нет столбцов связи исходного билета с дочерним или очередями:
сохраняются хеши секретов, срок, флаг разрешения приглашений и digest запроса.
Это ограничение хранения, а не невозможность корреляции: relay видит
параметры запроса в памяти, IP и время операций.

Отправка: `{ "id": "...", "payload": "<base64 bytes>" }`.
Получение: `{ "messages": [{ "id": "...", "payload": "..." }] }`.
Порядок получения — порядок принятия сервером; FIFO не даёт криптографической
гарантии порядка и проверяется клиентом отдельно.

Получение не удаляет сообщение. Подтверждение оставляет до истечения TTL
только ID, digest и служебные данные для дедупликации. Повтор того же ID с
другой полезной нагрузкой даёт `409`. После TTL дедупликация на сервере
заканчивается; клиент хранит своё состояние защиты от повторов.

Ограничения прототипа:

- 64 KiB декодированной нагрузки; HTTP body до 96 KiB.
- TTL 7 суток, проверяется при операциях и фоновом обслуживании.
- До 256 очередей.
- До 1024 неистёкших билетов, включая израсходованные; срок билета 1–86400 секунд.
- До 1024 записей на очередь, включая подтверждённые до TTL.
- До 4 MiB неподтверждённой нагрузки на очередь, 32 MiB на весь relay.
- Превышение квоты: `429`; некорректный JSON/base64/ID: `4xx`.
- Локальные серверные ошибки: `500` без SQL и секретов в ответе.

Лимиты являются настройками экспериментальной реализации и будут уточняться.
Очереди не имеют автоматического TTL. Вложения этим API не поддерживаются.
