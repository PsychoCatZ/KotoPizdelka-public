# Приглашения: ссылка, QR и подтверждение

## Приглашения и удаление: 0.2.3 (2026-10-05)

Обычный билет `issue-ticket.sh` создаёт только одну очередь. Для знакомства
по ссылке и QR нужен отдельный билет:

```powershell
ssh relay-host 'sudo /opt/kotopizdelka-relay/issue-ticket.sh --invite'
```

Сервер отклоняет обычный билет для этого действия с HTTP 403. Приложение
теперь показывает причину отказа. Откройте незавершённое приглашение →
«Продолжить подготовку», вставьте новый билет и повторите. Пустое поле
повторяет сохранённую попытку. Новая попытка использует прежний контакт,
ключи и очередь; перед заменой проверяется результат старого запроса,
чтобы восстановить создание после потерянного ответа сервера.

В заголовке каждой выбранной беседы или приглашения есть корзина.
Удаление требует подтверждения и удаляет данные только на этом устройстве:
историю, неотправленные сообщения, ключи и маршрут. У собеседника история
остаётся; уже опубликованная очередь на relay этим действием не удаляется.
Минимальные зашифрованные идентификаторы сохраняются для защиты от
повторного принятия старого приглашения и повторного использования очереди.
Это логическое удаление из базы, без гарантии стирания старых резервных
копий или следов в SQLite WAL. Другие контакты и профиль сохраняются.
Схема базы автоматически переходит с v1/v2 на v3 после проверки ключа;
откат клиента к версии до 0.2.3 после этого не поддерживается.

Windows: `KotoPizdelka-0.2.3-x64-setup.exe` или
`KotoPizdelka-0.2.3-Windows-x64.zip`.
Android: `KotoPizdelka-0.2.3-Android-arm64-2026-10-05.apk`.
Исходники: `private-messenger-invitations-delete-0.2.3-source-2026-10-05.zip`.
Установите обновления поверх существующих приложений, сохранив данные.
Повторное развёртывание relay для этих изменений не требуется.
Компактный QR 0.2.2 сохранён; знакомство с настоящей камерой всё ещё
проверяется пользователем после получения билета с нужными правами.


Основной сценарий Windows / Android использует одну ссылку
`kotopizdelka://invite#…` и локально созданный QR-код. Глобальный аккаунт,
телефон, email и никнейм не нужны. Старый ручной Offer/Reply v1 остаётся
доступен через «Старый формат приглашения»; прежние контакты сохраняются.

## Компактный QR в 0.2.2

Копирование / передача ссылки сохраняет обычный Base64URL(JSON) v2.
Только QR известных нативных экспортов использует
`kotopizdelka://invite#C2` и uppercase Base32 без padding (RFC 4648).
При сканировании, вставке или OS URI-активации renderer восстанавливает
обычную ссылку до передачи в Rust. Пользователь по-прежнему отдельно
принимает приглашение; создатель подтверждает знакомство. Это формат
переноса тех же данных, без сетевого сокращателя и новой модели доверия.

Binary layout после декодирования Base32, числа в big-endian:

| Offset | Байты | Поле |
| --- | --- | --- |
| 0 | 8 | expires_at, положительный safe integer |
| 8 | 16 | nonce offer |
| 24 | 32 | identity_key, исходный canonical Base64 без padding |
| 56 | 32 | one_time_key, исходный canonical Base64 без padding |
| 88 | 16 | queue_id |
| 104 | 32 | write token |
| 136 | 32 | reply secret |
| 168 | 32 | recipient_ticket |
| 200 | 2 | длина relay URL в UTF-8 |
| 202 | переменная | relay URL, ровно указанное число байт |

Hex-поля восстанавливаются в lowercase, протоколы и порядок JSON —
в исходную известную форму v2. При экспорте обязательно проверяется
побайтное равенство восстановленной и исходной ссылки; если оно не
выполняется, QR использует прежний payload. Неизвестные поля не удаляются
ради сокращения. При импорте длина ограничена 2300 символами до и после
восстановления; malformed / noncanonical encoding отвергается.
Окончательная проверка приглашения, срока, endpoint и ключей остаётся
в Rust после явного принятия, как раньше.

Полный example deployment-пример уменьшился с 966 до 415 символов, QR — со 117 до
69 модулей (M). Пользователь подтвердил чтение такого тестового QR камерой
после неудачи с полным кодом 0.2.1. Принятие настоящего приглашения новой
версии ещё проверяется. Для компактного QR обновите оба клиента до 0.2.2;
обычная копируемая ссылка совместима с прежними 0.2.x. Старые ссылки,
контакты и состояние сохраняются; relay / общий Caddy не обновляются.

## Быстрое знакомство v2

1. Владелец relay выдаёт создателю **invite-билет** через `issue-ticket.sh --invite`.
   Он разрешает одну очередь создателя и один билет очереди получателя без
   права создавать новые приглашения. Обычный билет на одну очередь не подходит;
   admin-токен клиенту не передаётся. Срок invite-билета по умолчанию — 24 часа.
2. Создатель открывает профиль, вводит HTTPS-адрес relay и этот билет, нажимает
   «Создать ссылку и QR-код». Ссылка действует **один час** с момента создания;
   интерфейс показывает окончание срока. Максимальная длина — 2300 ASCII-символов.
3. Покажите весь QR вместе с белым полем; в 0.2.1 доступно увеличенное
   представление. Собеседник открывает ссылку, вставляет её в «У меня есть приглашение» или
   сканирует QR на Android и явно нажимает «Принять приглашение». Отдельный
   билет и адрес relay ему не нужны: очередь создаётся на том же relay,
   зашифрованный Reply передаётся автоматически.
4. Создатель получает запрос и явно нажимает «Подтвердить знакомство».
   Зашифрованная служебная команда Olm завершает настройку; она не появляется
   в истории чата. После её получения обе стороны могут написать первыми.

При включённой foreground-синхронизации Reply и подтверждение приходят, пока
открытый профиль виден на экране. В ручном режиме используйте «Синхронизировать».
Точные параметры очередей, Reply и служебного конверта сохраняются до HTTP
в зашифрованном состоянии и используются повторно после ошибки / открытия
профиля. Истёкшее незавершённое приглашение требует новой ссылки.

## Личность и обращение со ссылкой

Подтверждение знакомства означает принятие ответа обладателя ссылки.
**Владение ссылкой не подтверждает личность.** Новый контакт имеет пометку
«Личность не проверена». После настройки откройте «Проверить собеседника»
на обоих устройствах, сравните весь общий код лично или по заранее доверенному
независимому каналу, затем явно выберите «Отметить личность проверенной».
Эта отметка сохраняется только в вашем профиле и не подтверждает проверку
на устройстве собеседника.

Ссылка содержит публичные ключи, write capability, секрет защиты Reply и
билет получателя. Передавайте её одному выбранному человеку: скопировавший
ссылку может занять место получателя. Она не даёт read capability или ключ
базы. Срок ссылки не является отзывом уже созданного контакта. Отзыв и
ротация capabilities пока не реализованы.

QR создаётся в приложении без сетевого QR API. Android-сканер использует
journeyapps 4.3.0 и ZXing core 3.4.1; кадры распознаются на устройстве.
Разрешение камеры запрашивается только после
нажатия «Сканировать QR-код». После неудачного исходного чтения 0.2.1
проверяет повороты бинарной матрицы в памяти. Изображения не загружаются
на сервер. Отказ в разрешении или отсутствие камеры оставляет вставку
ссылки доступной.

При запуске по URI и в уже открытом приложении ссылка ожидает в памяти до
открытия профиля и явного принятия; переход не создаёт контакт автоматически.
Windows передаёт обычный повторный запуск в существующее окно; лабораторные
профили остаются отдельными процессами. ОС, буфер обмена и приложение,
через которое передана ссылка, могут видеть её содержимое. Другой обработчик
custom scheme может перехватить URI. Некоторые мессенджеры не делают такую
ссылку кликабельной — скопируйте её целиком и вставьте в приложение.
HTTPS-страницы перехода нет.

Для v2 нужен relay 0.2.0 с pair endpoint; Caddy менять не требуется.
Пользователь подтвердил прохождение `update.sh --check` на немецком VPS;
результат `--update` отдельно не сообщён. Исправление QR 0.2.1 не требует
дополнительного обновления уже установленного backend 0.2.0. Новый сценарий,
запуск по URI и сохранение профиля при обновлении на физических устройствах
ещё требуют проверки. История результатов: [VALIDATION.md](VALIDATION.md).
Фоновая доставка и push этим изменением не добавляются.

новой ссылки. Вставка полной ссылки остаётся доступна независимо от камеры.

## Старый формат Offer/Reply v1

Следующие разделы описывают сохранённый ручной API и расширенный сценарий.
Каждая сторона передаёт отдельный артефакт и независимо проверяет его полный
отпечаток; получателю нужен собственный билет на очередь.

### Граница доверия v1

Приглашение содержит протокол `KotoPizdelka.invitation.v1`, роль Offer/Reply,
случайный 128-битный nonce, публичный Olm bundle и write endpoint:
URL relay, queue ID и write bearer token. Reply дополнительно содержит
отпечаток **полного исходного Offer**. Собственная read capability в экспорт
не попадает и сохраняется локально в зашифрованном состоянии.

Отпечаток — SHA-256 канонического представления всех этих полей с отдельным
назначением формата, 64 шестнадцатеричных символа нижнего регистра.
Порядок полей во входном JSON не меняет отпечаток после разбора.
Проверяется полный артефакт: подмена адреса или токена обнаруживается так же,
как подмена ключей. Отдельных подписей и собственных криптографических
примитивов здесь нет; после настройки сообщения защищает выбранная реализация Olm.

Хеш сам по себе не подтверждает владельца. Получатель должен знать ожидаемый
отпечаток через независимый доверенный канал, например при личной сверке.
Если злоумышленник может заменить и приглашение, и присланный рядом хеш,
проверка будет бесполезна. Этот же принцип действует для Reply: проверка
Offer первой стороной не подтверждает ответившего человека второй стороне.

Артефакт чувствителен: любой его обладатель получает write capability и
может отправлять байты в очередь, расходуя её ресурсы. Он не получает право
чтения и ключи расшифрования. Приглашения, capabilities и полные маршруты
нельзя печатать в логи. Содержащие их типы не реализуют `Debug`.

### Последовательность v1

Низкоуровневый API заранее получает свежую очередь для каждой стороны и принимает
`ReceiveQueue { read, write }`. Оба endpoint должны относиться к одной
очереди и иметь разные токены. Вызывающий код отвечает за то, что очередь уже
создана и capabilities назначены правильно. API с готовой очередью не
обращается к relay и не принимает admin-токен.

Desktop использует `create_invitation_with_ticket` и
`accept_invitation_with_ticket`. Rust генерирует ID и разные read/write
capabilities, атомарно сохраняет их вместе с артефактом и ограниченным билетом,
затем создаёт очередь через HTTP. Только после подтверждения можно экспортировать
Offer/Reply. Сетевую ошибку продолжает `provision_queue` с тем же предложением;
новый контакт создавать не нужно. См. [QUEUE_TICKETS.md](QUEUE_TICKETS.md).

Правильное назначение opaque токенов на роли read/write обеспечивает код
выдачи очереди: по самим строкам валидатор не может определить эти права.
Повторное использование очереди в профиле отклоняется по нормализованному
URL и queue ID, включая контакты, созданные прежним API маршрутов.

1. Инициатор вызывает `create_invitation(queue)`. Новый контакт, исходный
   Offer и собственная read capability сохраняются одной транзакцией.
   Возвращаются локальный ID контакта, экспорт и отпечаток.
2. Собеседник проверяет независимый полный отпечаток Offer и вызывает
   `accept_invitation(offer, trusted_offer_fingerprint, own_queue)`.
   Его контакт связывается с проверенными публичными ключами инициатора.
   Сохраняются маршрут, локальная read capability, метка повторного импорта
   и Reply, привязанный к исходному Offer.
3. Инициатор проверяет независимый полный отпечаток Reply и вызывает
   `complete_invitation(contact, reply, trusted_reply_fingerprint)`.
   Внутри транзакции проверяется соответствие исходному Offer, связываются
   ключи ответившего, создаётся исходящая Olm-сессия и сохраняется маршрут.
4. Инициатор может добавить первое сообщение в outbox и вызвать `sync`.
   У ответившего входящая Olm-сессия появляется после успешного приёма этого
   сообщения; только затем он может добавить собственный ответ в outbox.

До шага 3 `route` инициатора и `sync` возвращают `SetupPending`; HTTP-запросов
не выполняется. Ответивший может синхронизировать входящую очередь после
шага 2, но до первого принятого сообщения у него ещё нет сессии для `enqueue`.
Ровно один участник инициирует Olm. Политика HTTPS совпадает с сетевым клиентом;
буквальный loopback HTTP допускается только при явном разрешении для теста.

### Сохранение, повтор и формат v1

После подтверждения создания очереди `export_invitation(contact)`
восстанавливает тот же сохранённый Offer или Reply после перезапуска,
без выпуска нового nonce или ключей. Ожидающее задание создания очереди
блокирует экспорт, завершение Offer и синхронизацию до успешного восстановления.
Завершение уже завершённого Offer отклоняется. Повтор принятого Offer
отклоняется по сохранённой метке его полного отпечатка, в том числе после
повторного открытия базы. Ошибка проверки не завершает исходящий Offer.

Настройка хранится в необязательном поле `setup` зашифрованного маршрута.
SQL-схема остаётся v2; новая программа читает старые маршруты без этого поля.
Старый бинарный файл отклоняет маршруты с `setup`. Используйте новую версию
для профилей с приглашениями; откат бинарного файла не поддерживается.

Экспорт имеет вид `koto-invite:v1:` + URL-safe Base64 без padding.
В нём сериализован JSON. Префикс, версия, роли, поля, длины и hex-значения
проверяются при разборе; неизвестные поля отклоняются. Это текстовый формат,
для ручной передачи; QR основного сценария 0.2.0 содержит ссылку v2.

| Ограничение | Значение |
|---|---|
| Текст экспорта | 8192 байта |
| JSON артефакта | 6144 байта |
| Локальная полезная нагрузка настройки | 8192 байта |
| Контакты, включая незавершённые приглашения | 128 на профиль |
| Общий логический объём encrypted blobs | 64 MiB |

Завершённые записи остаются в базе и сохраняют метку повторного импорта.
Срок действия, отзыв, удаление и pruning не реализованы. Защита от повтора
действует в текущем профиле; глобальной регистрации уже принятых приглашений
нет. Возврат старой валидной копии базы может убрать локальную метку и
остаётся вне гарантий прототипа.

### Локальный пример v1

~~~sh
cargo test --workspace --locked
cargo run -p messenger-client --example invitation_dialog --locked
~~~

Пример создаёт временный relay и два клиентских хранилища, настраивает
контакты обменом Offer/Reply, повторно открывает базы и выполняет диалог
с фиксированными тестовыми сообщениями. Экспорты и capabilities не печатаются.
Отпечатки передаются внутри контролируемого процесса; это проверка связи
полей и сохранения состояния, а не аутентификация личности человека.
Admin-токен используется только временным серверным fixture для создания
очередей и не входит в API приглашений. Ключи баз остаются в памяти;
пример не использует системное хранилище ключа.

Для Windows отдельно есть пример `windows_profile` с DPAPI. Android Keystore
реализован; отзыв и ротация capabilities остаются дальнейшей работой.
Relay по-прежнему видит сетевые метаданные;
приглашения не добавляют защиту от корреляции IP и времени обращений.
Результаты проверок: [VALIDATION.md](VALIDATION.md).

## Ссылки от аккаунта — 0.2.10

`CreateAccountLink` создаёт секрет разрешения и зашифрованное состояние
контакта до сети. `POST /v1/accounts/link-ticket` разрешён только по живой
сессии аккаунта. Relay хранит хеш билета, логин владельца и время выдачи;
это позволяет связать созданную очередь с аккаунтом владельца. Адресат
ссылки не определяется этим API. Содержимое переписки остаётся E2E.

Повтор выдачи того же разрешения идемпотентен и привязан к владельцу.
Ограничения: 12 новых ссылок на аккаунт за 24 часа и прежний общий лимит
активных билетов. Разрешение не принимается из renderer: его генерирует
Rust worker. Сеанс не отправляется на чужой relay. Незавершённая попытка
содержит исходный билет, очередь и ключи; после потери ответа и перезапуска
«Продолжить подготовку» использует их снова. После выхода из аккаунта
неавторизованную подготовку надо продолжать после повторного входа.

Ссылка по-прежнему действует час, рассчитана на одного получателя и
требует подтверждения знакомства владельцем. Подлинность личности
проверяется отдельно. Получатель может принять ссылку без аккаунта.
