# Клиентское хранилище — схема v2

`messenger-store` сохраняет состояние личных Olm-сессий, inbox, outbox,
ожидающие подтверждения, маршруты очередей и состояние обмена приглашениями
в SQLite. HTTP-операции
выполняет `messenger-client`; см. [NETWORK_CLIENT.md](NETWORK_CLIENT.md).

## Порядок операций

`enqueue(contact, text)` в одной `BEGIN IMMEDIATE` транзакции загружает
актуальное состояние контакта, шифрует сообщение, сохраняет **точный конверт**
и новое состояние ratchet. Только после успешного commit конверт можно
отправлять. Повторная отправка берёт тот же `id` и `payload` из
`pending_outbox`, без повторного шифрования. После ответа relay `202`
транспорт вызывает `mark_sent`; этот статус означает принятие сервером, а не
прочтение собеседником.

`accept(contact, envelope)` атомарно сохраняет расшифрованный текст в
зашифрованной записи inbox, конверт, новое состояние ratchet и флаг
ожидающего ACK. Только после commit можно подтверждать сообщение на relay.
`pending_acks` восстанавливает список после открытия базы; после ответа
relay `204` вызывается `mark_acked`.

Повтор уже принятого `id` считается `Duplicate` только при точном совпадении
сохранённого `payload`. Ratchet повторно не расходуется. Даже после
`mark_acked` такая доставка снова ставит флаг ACK. Другой payload с тем же
ID даёт `Conflict`; ошибочную доставку подтверждать нельзя. Проверка
дубликата выполняется перед квотами новых сообщений.

Каждая изменяющая операция загружает состояние внутри транзакции; mutable
cache контактов отсутствует. Ошибка SQL или превышение квоты откатывает
запись и новое состояние. `insert_contact`, `bind_peer` и `start_session`
также сохраняют изменения транзакционно. Отпечаток для `bind_peer` должен
приходить из независимого доверенного канала, как описано в
[E2EE_DECISION.md](E2EE_DECISION.md).

## Маршруты и миграция

`ContactRoute { send, receive }` содержит два `QueueEndpoint`:
`relay_url`, `queue_id` и bearer `token`. `set_route(contact, &route)`
транзакционно назначает маршрут существующему контакту только один раз;
повтор возвращает `RouteAlreadySet`. `route(contact)` читает его после
проверки AEAD; отсутствие маршрута даёт `NotFound`, незавершённый исходящий
Offer — `SetupPending`. URL, queue ID и токен
полностью зашифрованы вместе, а AAD связывает запись с database ID,
contact ID и назначением `route`.

Хранилище проверяет длину и hex-формат queue ID и токенов, непустой URL
длиной до 2048 байт. Разбор URL и политику TLS выполняет сетевой клиент.
Ротация маршрутов не реализована.

Приглашения используют необязательное поле `setup` внутри зашифрованной
записи маршрута. Оно содержит сохранённый артефакт, локальную read capability,
признак готовности и постоянную метку повторного импорта. `insert_setup_contact`
атомарно сохраняет новый контакт, маршрут и это состояние. В ручном v1 завершение Offer
сравнивает ожидаемое состояние внутри транзакции, связывает проверенные ключи
собеседника, создаёт исходящую Olm-сессию и заменяет маршрут. Локальная read
capability и метка повторного импорта при завершении не меняются.

Для создания очереди по [билету](QUEUE_TICKETS.md) payload также хранит
необязательное ожидающее задание: секрет билета и уже выбранные ID/read/write
capabilities доступны только в зашифрованном состоянии. Это состояние
сохраняется до HTTP. Замена билета и снятие задания после успеха сравнивают
ожидаемую запись внутри транзакции; криптографические данные приглашения,
метка повтора и локальная read capability сохраняются. Ошибка сети оставляет
точную попытку для продолжения после повторного открытия профиля.

В 0.2.0 encrypted setup также хранит quick-ссылку, срок, роль, точную попытку
pair / recipient queue, зашифрованный Reply, служебный конверт и локальную
отметку проверки личности. Служебная команда Olm и продвинутое состояние
ratchet сохраняются одной транзакцией, без записи пользовательского сообщения
в историю / outbox. Получатель сохраняет её принятие и готовность до ACK;
повторное получение не требует повторного расходования ratchet.
Ссылка связывает ключи без утверждения о личности человека. Независимая
проверка общего кода и явная отметка сохраняются отдельно от готовности чата.

После перезапуска приложение может экспортировать ту же quick-ссылку либо
Offer/Reply старого формата и продолжить сохранённую сетевую попытку.
Завершённые записи сохраняются для отклонения повторного импорта того же Offer
в текущем профиле. Эти записи входят в общие квоты контактов и encrypted blobs;
очистка и отзыв пока не реализованы. Quick-ссылка имеет срок один час;
у старого v1 срока нет. Подробнее:
[INVITATIONS.md](INVITATIONS.md).

При открытии базы v1 сначала проверяется ключ, затем в той же
`BEGIN IMMEDIATE` транзакции добавляется таблица `routes` и версия
повышается до 2. Состояния ratchet, inbox и outbox сохраняются без
перешифрования. Неверный ключ не запускает миграцию; ошибка SQL откатывает
и новую таблицу, и изменение версии. Отсутствующая таблица `routes`
в базе v2 считается повреждением и не создаётся заново автоматически.

SQL-схема остаётся v2. Новая программа читает старые записи маршрутов без
`setup`. Старый бинарный файл отклоняет новые записи с этим полем из-за
строгого формата; совместимость поддерживается при обновлении вперёд.
Профиль после использования новых quick-контактов следует открывать 0.2.0
или новее; откат бинарного файла не поддерживается. Чтение прежних контактов
сохраняется, но обновление на физических устройствах требует проверки.

## Порядок доставки

Outbox и история выдаются по возрастающему локальному `seq`, а не по
случайному message ID. История поддерживает курсор `after_sequence`;
выборки ограничены 100 записями. После обработки первой страницы pending
сообщений следующая выборка выдаёт оставшиеся.

FIFO хранилища не гарантирует порядок сети. В текущем core Olm сохраняет
до 40 skipped keys на receiving chain. Транспорт должен отправлять
сообщения одного контакта последовательно или использовать небольшое окно
с контролем порядка; произвольная перестановка сотен сообщений может
сделать старые сообщения нерасшифровываемыми.

## Ключ и защита на диске

Вызывающий код передаёт стабильный случайный `messenger_core::StorageKey`.
Ключ в базе не хранится. `ClientWorker::open_system` загружает его через
Windows DPAPI или Android Keystore. Android backend реализован и входит в
ARM64 APK; пользователь подтвердил первое / повторное открытие профиля.
Первый обмен с Windows, история после заявленного принудительного закрытия
Android, отложенное получение и история после перезагрузки телефона подтверждены
пользователем; новые сообщения после неё и отказы Keystore ещё не проверены. Подробности в
[STORAGE_KEYS.md](STORAGE_KEYS.md).
Потеря ключа лишает доступа к базе. Схема и зашифрованный контрольный
маркер ключа инициализируются одной `BEGIN IMMEDIATE` транзакцией.
Неверный ключ существующей базы отклоняется до изменений схемы, данных
или режима журналирования.

Тексты и точные конверты inbox/outbox, полное состояние контактов, маршруты
и состояние приглашений, включая локальные read capabilities,
зашифрованы XChaCha20-Poly1305 до передачи в SQLite. Внешний AEAD-wrapper
связывает записи через AAD с версией формата, database ID, назначением,
contact ID и message ID, где применимо. Это обнаруживает подмену ciphertext
и перестановку зашифрованных записей между контекстами.

Открытыми остаются локальные идентификаторы, направление, `seq`, `pending`,
число записей и размеры ciphertext. `seq` и `pending` не аутентифицированы:
их злонамеренная правка может изменить порядок или скрыть ожидающую
операцию. Защиты от удаления записей, возврата к старой валидной базе
или компрометации устройства нет.

При компрометации storage key сохранённая история становится доступна,
даже если старые ключи сообщений уже удалены из текущего ratchet. SQLite/WAL
и резервные копии могут сохранять прежние зашифрованные состояния; безопасное
стирание и политика резервного копирования пока не реализованы.

## Сохранность и проверки

Для успешно открытого файлового хранилища включаются WAL, `synchronous=FULL`,
foreign keys и busy timeout 5 секунд. Сохранность при аварии зависит от
файловой системы и устройства, которые должны корректно выполнять
блокировки и синхронизацию SQLite. `:memory:` не обеспечивает сохранение
после завершения процесса.

Linux-тесты моделируют перезапуск закрытием и повторным открытием базы,
инъецируют SQL abort через triggers, проверяют совместное использование
двумя handles, конкурентное первое открытие, неверный ключ, миграцию и
повреждение записей, включая маршруты. Это не испытания отключения питания
и не доказательство сохранности на произвольном устройстве.
Результаты текущего этапа приведены в [VALIDATION.md](VALIDATION.md).

## Пределы прототипа

| Ограничение | Значение |
|---|---|
| Контакты | 128 |
| История контакта, оба направления вместе | 10 000 записей |
| Pending при добавлении нового сообщения | 256 на контакт и направление |
| Сумма ciphertext сообщений, состояний и маршрутов | 64 MiB |
| Страница истории, outbox или ACK | 100 записей |

64 MiB — логический объём encrypted blobs, а не предел размера файлов
SQLite и WAL. Повтор принятого сообщения может снова поставить ACK даже
при достигнутом pending лимите: уже сохранённое сообщение остаётся
подтверждаемым. Удаления и pruning пока нет; подтверждение снимает pending,
но сохраняет историю и запись для распознавания повторов.

Нативный [UI Windows и Android](DESKTOP.md) читает историю и добавляет сообщения
через последовательный Rust actor. Защита от malicious rollback остаётся
отдельным будущим этапом.

Пример локального диалога с повторным открытием баз:

```sh
cargo run -p messenger-store --example durable_dialog --locked
```

Пример использует временные базы и держит ключи в памяти. Доверенные
контакты создаются в одном процессе; ответы relay моделируются без сети.
