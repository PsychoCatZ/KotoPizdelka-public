# Защищённый ключ профиля

`messenger-platform` сохраняет случайный 32-байтный ключ базы под защитой
DPAPI текущего пользователя Windows. `ClientWorker::open_system(path, false)`
подключает эту защиту к клиентскому хранилищу. Дополнительные установщики,
пароль приложения и передача ключа через командную строку не нужны.
Первый [desktop-клиент](DESKTOP.md) использует этот API через Rust actor.
Каталог данных выбирает нативная оболочка, а не webview; сам ключ и read
capabilities в IPC-ответы не попадают.

Android использует отдельный backend Android Keystore, описанный ниже.
Он сохраняет тот же порядок блокировки и не меняет файлы Windows.

В 0.2.0 quick-ссылки, секреты настройки и локальная отметка проверки личности
хранятся в зашифрованном профиле под тем же ключом. URI handoff держит ожидающую
ссылку в памяти до явного принятия; QR создаётся / распознаётся локально.
Renderer сохраняет только boolean режима синхронизации, не ссылки, ключи
или контактные ID. Передача через ОС / буфер обмена не входит в защиту базы.
Обновление 0.1.x → 0.2.0 с сохранением профиля ещё требует проверки на устройствах.

## Файлы и порядок создания

Для базы `profile.sqlite` используется соседний файл
`profile.sqlite.key.dpapi`. Он содержит заголовок формата и непрозрачный
DPAPI blob. Сам ключ не записывается открытым текстом. Объект StorageKey
в памяти нужен для работы; после использования его буфер очищается.

Клиент сначала удерживает `profile.sqlite.worker.lock`, затем загружает
или создаёт ключ и только после этого открывает SQLite. Блокировка сохраняется
до завершения работы клиента.

| База | Файл ключа | Действие |
|---|---|---|
| Отсутствует | Отсутствует | Создать ключ, защитить DPAPI, сохранить, затем создать базу |
| Отсутствует | Корректный | Использовать сохранённый ключ, затем создать базу |
| Существует | Корректный | Раскрыть ключ через DPAPI и проверить его по служебной записи базы |
| Существует | Отсутствует | MissingKey; новый ключ не создаётся |
| Любое состояние | Повреждённый или недоступный | Ошибка; файл не заменяется |

Корректный ключ, оставшийся после ошибки создания базы, используется при
повторной попытке. Ошибка открытия SQLite не удаляет уже сохранённый ключ.
Ключ от другой базы того же пользователя может успешно раскрыться в DPAPI,
но проверка SQLite отклонит его и не переинициализирует существующие данные.

Сначала полностью записывается и синхронизируется временный защищённый файл
в том же каталоге. В Windows публикация выполняется через MoveFileExW
с WRITE_THROUGH, без REPLACE_EXISTING. Опубликованный файл не перезаписывается.
При загрузке он снова синхронизируется перед открытием базы.
Отключение питания и поведение конкретного накопителя не проверялись;
безусловная сохранность при аппаратных сбоях не обещается.

## Область защиты

Используются CryptProtectData / CryptUnprotectData, фиксированное назначение
формата в additional entropy и UI_FORBIDDEN. Machine-scope flag не включается.
Доступ зависит от контекста DPAPI пользователя Windows, а не от глобального
идентификатора мессенджера.

Ответ API принимается только после успешного вызова. Результат раскрытия
должен иметь ровно 32 байта. Память результата очищается и освобождается;
ошибки не содержат ключ, blob, пути профиля или подробности WinAPI.
Размер защищённого blob ограничен 64 KiB.

DPAPI не защищает от программы, которая уже выполняется от имени того же
пользователя и может обращаться к его DPAPI. Он также не предотвращает
удаление файлов, подмену профиля, возврат старой корректной копии базы или
компрометацию устройства.

## Восстановление и другие платформы

Копирование SQLite и DPAPI sidecar само по себе не гарантирует переносимость
профиля на другой компьютер или в другую учётную запись. Для раскрытия
требуется соответствующий контекст DPAPI. Переносимый экспорт, восстановление
при потере профиля Windows и ротация ключа пока не реализованы.

Прежний `ClientWorker::open(path, key, ...)` остаётся низкоуровневым API для
явно переданного ключа и облачных тестов. `open_system` не импортирует такой
существующий профиль автоматически: без sidecar он вернёт MissingKey.
Демонстрационные примеры предыдущих этапов используют временные базы.

В Linux `open_system` возвращает UnsupportedPlatform до создания базы,
lock-файла или ключа. Открытого fallback-файла нет.

## Android Keystore

Нативная Android-оболочка передаёт JavaVM через
`messenger_platform::initialize_android`. Инициализация не открывает профиль,
не создаёт ключи и не добавляет команды webview. До получения JavaVM
`open_system` возвращает UnsupportedPlatform без создания файлов.
Вызовы защиты и раскрытия выполняются на потоке Rust actor, который
подключается к VM на время операции; JNI-объекты не покидают этот вызов.

Для одной базы `profile.sqlite` сохраняется
`profile.sqlite.key.android-keystore`. Формат имеет собственный заголовок,
12-байтный IV, 32 байта зашифрованного ключа и 16-байтный тег GCM.
Additional authenticated data связывает шифротекст с назначением и версией
формата. Случайный IV создаёт Android Cipher; повторное использование
зафиксированного IV приложением не предусмотрено.

AES-256 ключ обёртки создаётся в провайдере AndroidKeyStore с назначением
encrypt/decrypt, режимом GCM, без padding и с требованием случайного IV.
Приложение не экспортирует его байты. Alias
`ru.kotification.kotopizdelka.storage-key.v1` ограничен UID приложения и служит
одному Android-профилю; он не является адресом пользователя или контакта.
Наличие StrongBox или аппаратного хранилища на конкретном устройстве не
предполагается и пока не проверялось.

Создание alias допустимо только при первом создании профиля: база и sidecar
должны отсутствовать, а worker lock уже должен удерживаться. Если alias
остался после сбоя до записи sidecar, он используется повторно. При раскрытии
существующего sidecar новый alias никогда не создаётся. Потеря alias,
неподходящий тип ключа, ошибка аутентификации GCM или сбой Keystore приводят
к отказу; существующие файлы не заменяются и не удаляются.

Sidecar публикуется атомарно без перезаписи существующего файла. Временный
защищённый файл имеет закрытые разрешения и синхронизируется вместе с
каталогом. В JNI открытые byte arrays очищаются после копирования и после
ошибок; временные Rust-буферы используют Zeroizing. Внутренняя память
Android криптографического провайдера управляется самим провайдером.
Исключения Java очищаются без вывода подробностей в журнал или UI.

Копирование базы и sidecar на другой телефон не переносит Keystore alias.
Нативный manifest задаёт `allowBackup="false"`; `backup_rules.xml` и
`data_extraction_rules.xml` исключают корень данных приложения, включая
cloud backup и перенос между устройствами. Эти XML вошли в собранный APK;
поведение на конкретном телефоне ещё не проверено. Удаление приложения или
очистка его данных приводит к потере профиля и ключа.
Экспорт с переносимым ключом и восстановление после потери
alias не реализованы. Root-доступ, компрометация работающего приложения,
удаление файлов и откат корректной копии данных остаются вне этой защиты.

## Проверка

На Windows:

~~~powershell
cargo test --workspace --locked
cargo run -p messenger-client --example windows_profile --locked
~~~

Пример создаёт временный профиль. Первый дочерний процесс сохраняет контакт
и сообщение в outbox, второй восстанавливает историю и ожидающую отправку.
Между процессами передаются только путь и действие; ключ не передаётся.
В конце временный профиль удаляется.

В облаке Linux проверены жизненный цикл файла с приватным аутентифицированным
тестовым provider и отказ неподдерживаемой платформы без побочных эффектов.
Windows DPAPI backend и его тесты прошли компиляционную проверку под MSVC.
Пользователь затем сообщил об отсутствии ошибок при выполнении предложенных
команд на Windows, включая тесты и `windows_profile`. Это пользовательское
подтверждение нативной работы; вывод запуска в облаке не собирался.
Состав текущих проверок указан в [VALIDATION.md](VALIDATION.md).

Для Android добавлены проверки отказа повреждённого формата до JNI и
сохранения sidecar при потере OS-защиты, включая состояние без базы.
Это проверки формата и общего жизненного цикла на хосте. Они не подтверждают
работу AndroidKeyStore. Backend прошёл `cargo check` и Clippy с запретом
предупреждений для `aarch64-linux-android`, затем собран полный ARM64 release APK.
JNI-сигнатуры и вызовы Keystore проверяются при работе Java на устройстве.
Позднее пользователь подтвердил первое создание / открытие Android-профиля
и повторное открытие после закрытия приложения в контексте инструкции;
[подтверждение и границы](VALIDATION.md#первый-android-профиль-подтверждение-пользователя).
Первый обмен с Windows подтверждён пользователем; [границы проверки](VALIDATION.md#первый-диалог-windows-и-android-подтверждение-пользователя).
Позднее подтверждены история после заявленного принудительного закрытия Android
и отложенное получение; [границы проверки](VALIDATION.md#закрытый-android-получатель-и-повторная-синхронизация).
Пользователь также подтвердил открытие профиля и сохранение истории после
перезагрузки телефона в контексте инструкции; [границы подтверждения](VALIDATION.md#история-android-после-перезагрузки-подтверждение-пользователя).
Логи JNI / Keystore не предоставлены. Отказ при потере alias и обмен новым
сообщением после перезагрузки ещё не проверены.
Инструкция установки и проверки — [ANDROID_SETUP.md](ANDROID_SETUP.md).
