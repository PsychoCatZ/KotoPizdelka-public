# MVP: статус разработки 0.2.0

## Границы

Desktop + Android, один экземпляр клиента на человека, личные текстовые диалоги.
Контакты добавляются одноразовыми приглашениями / QR-кодом. Нет глобального
имени, телефонного номера, поиска пользователей, групп, вложений или звонков.

Серверу не доверяем содержимое. Ссылка / QR разрешает знакомство, но не
доказывает личность: обе стороны независимо сравнивают общий код и явно
сохраняют локальную отметку. Старый v1 использует полные отпечатки Offer / Reply.
Компрометация устройства и глобальный сетевой наблюдатель вне гарантий MVP.
Прямой HTTPS раскрывает IP и время обращения серверу. Отсутствие аккаунтов
не устраняет корреляцию очередей по сетевым данным.

## Компоненты

1. Relay: хранение непрозрачных конвертов, получение, подтверждение, TTL
   и ограниченные билеты на создание очередей.
2. Rust core: интеграция проверенного E2EE и состояние диалога.
3. Client store: зашифрованные inbox/outbox и состояние сессии в одной транзакции.
4. HTTP client: проверяемый обмен приглашениями, доставка из outbox,
   сохранение inbox перед ACK и восстановление.
5. Rust actor: последовательные команды профиля и данные для интерфейса.
6. Tauri v2: Windows UI и ранний Android UI; ARM64 release APK собран.
   Первое / повторное открытие Android-профиля подтверждено пользователем;
   первый диалог Windows ↔ Android подтверждён пользователем.

На каждый контакт предусмотрены две очереди, по одной на направление.
Внутренний ID очереди не является глобальным ID пользователя.

## Критерий приёмки

Desktop отправляет сообщение, когда Android-клиент закрыт. После открытия
Android получает и расшифровывает его. Перезапуск клиента и relay сохраняет
возможность общения. Повторная отправка не создаёт дубликатов в UI.
Этот критерий ещё не выполнен: продолжение общения после перезапуска relay
и повторная отправка того же конверта на физических устройствах не подтверждены.
История после перезагрузки телефона подтверждена пользователем; обмен новым
сообщением после неё ещё не зафиксирован.

## Обязательные свойства клиента

- Проверенный E2EE-протокол; примитивы не разрабатываются самостоятельно.
- Подтверждение relay только после надёжного локального сохранения сообщения.
- Дедупликация по ID и проверка криптографической подлинности на клиенте.
- Ключи и секретные capabilities не попадают в UI-логи и аналитику.
- Безопасное хранение состояния, анализ резервного копирования и rollback.

Текущий `messenger-store` реализует локальную часть этих требований.
Ключ можно явно передать либо открыть профиль через Windows DPAPI или
реализованный Android Keystore. Первое / повторное открытие Android-профиля
подтверждено пользователем; отказ при потере alias ещё не проверен на телефоне.
Интеграционный тест с relay
моделирует перезапуски и повторную доставку. `messenger-client` связывает store
с настоящим HTTP. Windows и Android UI вызывают последовательный Rust actor;
автоматическая фоновая работа ещё впереди.
Подробности и ограничения описаны в [CLIENT_STORE.md](CLIENT_STORE.md).
Приглашения описаны в [INVITATIONS.md](INVITATIONS.md). Низкоуровневый API
принимает готовую очередь, а основной UI использует один invite-билет
создателя и билет получателя внутри ссылки. Старый ручной сценарий принимает
отдельный обычный билет каждой стороны. Точные параметры сохраняются до HTTP.
См. [QUEUE_TICKETS.md](QUEUE_TICKETS.md) и [DESKTOP.md](DESKTOP.md).
Установка Android Studio завершена со слов пользователя. В облаке собран
ARM64 APK с SDK 37.0 и NDK r29; пользователь подтвердил запуск на телефоне
и первое / повторное открытие профиля, затем первый двусторонний обмен с Windows.
См. [ANDROID_SETUP.md](ANDROID_SETUP.md).

## Известные ограничения relay

Один узел, без репликации. Удаление сообщений из SQL не означает безопасное
стирание с диска: WAL, файловая система и резервные копии могут сохранять байты.
Квота полезной нагрузки не ограничивает физический размер SQLite; для VPS
дополнительно нужны лимит тома и обслуживание базы. Пакет TLS-развёртывания
установлен на немецком VPS; лимиты ресурсов настроены, но поведение при
достижении лимитов и изоляция служб ещё не проверены на VPS.
HTTP rate limiting и ротация capabilities пока не реализованы.
Билеты на очереди выдаёт владелец локальной командой; web-панели для него нет.
Обмен клиентскими приглашениями не предоставляет
административных прав на relay.

Установка серверного пакета описана в [RELAY_DEPLOYMENT.md](RELAY_DEPLOYMENT.md).
