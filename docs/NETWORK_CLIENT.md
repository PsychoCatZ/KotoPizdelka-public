# Сетевой клиент: первый эксперимент

`messenger-client` связывает зашифрованное клиентское хранилище с HTTP API
relay. Библиотеку использует [UI Windows и Android](DESKTOP.md) через Rust actor.
В 0.1.1 видимый UI планирует автоматические вызовы существующего API;
воспроизводимые примеры остаются отдельно, фонового получения нет.
В 0.2.0 добавлен quick-обмен через одну ссылку / QR и relay pair endpoint;
старый ручной API Offer/Reply сохранён.
Для Windows подключён DPAPI, для Android — Keystore;
подробности в [STORAGE_KEYS.md](STORAGE_KEYS.md).

## Проверка на Windows / Linux

В каталоге проекта:

~~~sh
cargo test --workspace --locked
cargo run -p messenger-client --example network_dialog --locked
cargo run -p messenger-client --example invitation_dialog --locked
~~~

Отдельно запускать relay не нужно. Пример создаёт сервер на случайном
локальном порту и два временных клиентских хранилища. Каждая клиентская
операция выполняется в новом процессе. Первый клиент сохраняет сообщение
и выходит; до его повторного запуска сервер ещё не получает сообщение.
Затем проверяются отправка, получение, подтверждение, ответ, повторная
синхронизация без дубликатов и история обоих клиентов.

Ключи временных баз остаются в родительском процессе и передаются детям
через stdin. Они не записываются в файл, аргументы командной строки или
переменные окружения. Пример печатает только два заранее заданных текста
и сообщение об успехе. После завершения базы удаляются. Это способ проверки
транспорта, а не способ хранения ключа реального пользователя.

`invitation_dialog` отдельно проверяет настройку контактов через сохранённые
Offer/Reply и HTTP-диалог. Отпечатки известны контролируемому тестовому процессу;
пример не проверяет личность человека. Ключи временных баз остаются в памяти.
Подробности в [INVITATIONS.md](INVITATIONS.md).

## Контракт обработчика

Приложение создаёт
`ClientWorker::open(database_path, storage_key, allow_loopback_http)`.
Путь должен указывать на файловую базу в существующем каталоге.
Через `store()` доступны локальные операции, включая `enqueue`.
`ClientWorker::open_system(path, allow_loopback_http)` открывает профиль
с ключом под защитой Windows DPAPI. Worker lock покрывает создание ключа
и открытие SQLite. Android использует Keystore; остальные платформы
возвращают UnsupportedPlatform.

Вызов `sync(contact)` выполняет один ограниченный проход:

1. Загружает сохранённый маршрут и проверяет обе конечные точки.
2. Отправляет ранее сохранённые ACK; снимает pending только после HTTP 204.
3. Последовательно отправляет точные конверты outbox; отмечает принятие
   сервером только после HTTP 202.
4. Получает до 100 конвертов. Проверяет формат и пределы всей страницы.
5. Для каждого конверта вызывает атомарный `accept`, затем DELETE на relay,
   затем сохраняет отметку ACK.

Для старого формата v1 контакт с ещё не подтверждённым созданием очереди возвращает
`QueueProvisionPending` до HTTP-запросов. Контакт с исходящим Offer до принятия
проверенного Reply возвращает `SetupPending`. У ответившей стороны маршрут уже доступен
для получения; `enqueue` становится возможен после первого успешно принятого
сообщения, которое создаёт входящую Olm-сессию.

Для quick-контакта `sync` продолжает сохранённую подготовку очереди, отправляет
зашифрованный Reply и получает служебные ответы. Создатель явно вызывает
`confirm_quick_invitation`; типизированная команда Olm создаёт входящую
сессию получателя и готовность без пользовательского первого сообщения.
Reply / служебные команды не попадают в историю. Точные конверты и состояние
сохраняются до отправки / ACK; потеря HTTP-ответа продолжает ту же попытку.

Ранее принятый точный конверт распознаётся как повтор. Новый текст с
использованным ID отклоняется. Ошибка останавливает проход; уже сохранённый
прогресс остаётся в базе. Следующий вызов продолжает ожидающие операции.
Повторять `enqueue` для повторной попытки доставки нельзя: это создаст новое
сообщение. HTTP 202 означает приём сервером, а не доставку или прочтение.

Проход ограничен первой страницей outbox, ACK и получения. Приложению
предстоит организовать дальнейшие проходы, паузы, отмену и отображение ошибок.
Внутри команды клиента нет бесконечного retry. Foreground-планировщик UI
0.1.1 может начать следующую команду после паузы; HTTP API и backend не менялись.

## Один сетевой обработчик на базу

На время жизни `ClientWorker` удерживается файловая блокировка
`<database>.worker.lock`. Второй обработчик того же канонического пути
получает `AlreadyRunning`. После завершения процесса ОС освобождает
блокировку; пустой lock-файл остаётся на диске.

Блокировка согласительная: приложение обязано использовать этот обработчик
для сетевой работы. Открытие обычного `ClientStore` её не проверяет.
Жёсткие ссылки на файл, подмена файлов и злонамеренный локальный процесс
вне этой гарантии. Сама SQLite сериализует отдельные транзакции, но не
заменяет блокировку полного сетевого обмена.

## Маршруты и HTTP

Для контакта сохраняются две независимые конечные точки:
`ContactRoute { send, receive }`, каждая содержит URL relay, queue ID и
bearer token. Запись зашифрована и привязана к базе и контакту.
`set_route` разрешён один раз; ротация очередей пока не реализована.
Высокоуровневые `create_invitation`, `accept_invitation` и
`complete_invitation` сохраняют маршрут и состояние настройки атомарно;
настройка исходящего Offer v1 завершается только проверенным Reply.
Методы `create_invitation_with_ticket` и `accept_invitation_with_ticket`
добавляют создание очереди по ограниченному билету. Они сохраняют точные
параметры и ожидающее задание до HTTP. `provision_queue` продолжает его после
ошибки связи, с прежним либо новым билетом. См. [QUEUE_TICKETS.md](QUEUE_TICKETS.md).

`create_quick_invitation(relay_url, invite_ticket)` сохраняет точные параметры
до pair endpoint. Invite-билет создаёт очередь владельца и один ограниченный
билет получателя. `accept_quick_invitation(link)` берёт адрес и билет из
ссылки, создаёт свою очередь на том же origin и отправляет защищённый Reply.
Отдельный билет / admin-токен получателю не нужен. Ссылка действует один час,
принимается строго в ограниченном custom-scheme формате длиной до 2300.
Новый endpoint требует обновления relay; работа прежних очередей сохраняется.

URL должен указывать на корень сервера, без credentials, query, fragment
или дополнительных путей. Пути API строятся из проверенных hex ID.
Bearer передаётся в отдельном sensitive Authorization header.
Redirects отключены, токен не переносится на адрес из ответа сервера.

По умолчанию разрешён HTTPS с проверкой сертификатов и системными корнями
доверия. HTTPS использует обычную proxy policy reqwest, включая окружение;
автоматического перехода на прямое соединение при ошибке proxy нет.
Для локальных тестов можно явно разрешить HTTP к буквальному loopback IP
из 127.0.0.0/8 или ::1. Такой запрос идёт напрямую, без внешнего proxy.
HTTP к имени localhost, адресу LAN или VPS этим исключением не разрешён.

Connect timeout — 5 секунд, timeout запроса — 15 секунд.
Ответ получения ограничен 9 MiB как по Content-Length, так и во время
чтения потока; максимум 100 сообщений проверяется до первого `accept`.
Underlying HTTP errors, URL, capabilities и тела ошибок не включаются
в ошибки библиотеки. Тексты истории возвращаются приложению по его запросу.

## Доверие и ограничения

В `network_dialog` публичные ключи и маршруты создаются внутри доверенного
процесса; низкоуровневый fingerprint ядра связывает только crypto bundle.
Ручной v1 [обмена приглашениями](INVITATIONS.md) проверяет SHA-256 полного артефакта:
ключи, роль, nonce, URL, queue ID, write capability и привязку Reply к Offer.
Обеим сторонам нужен независимый доверенный источник полного отпечатка.
Сам хеш рядом с артефактом в недоверенном сообщении доверия не добавляет.
Собеседнику передаётся только write capability нашей входящей очереди;
read capability остаётся на нашей стороне. Приглашение чувствительно:
любой его получатель может отправлять байты в эту очередь, но не читать её
и не расшифровывать сообщения. Общего административного токена в API
приглашений нет. Desktop получает свежую очередь по отдельному билету
владельца relay; read/write capabilities генерируются в Rust и сохраняются
локально до погашения билета.

Quick v2 связывает криптографические ключи обладателя ссылки без подтверждения
личности. После служебного обмена обе стороны получают общий код; его нужно
сравнить по независимому доверенному каналу и явно отметить проверенным.
Отметка локальна. Ссылка содержит секреты настройки и не должна попадать в
логи; её видят ОС / приложение передачи, custom-scheme обработчик может
перехватить URI. QR создаётся и сканируется локально, без сетевого QR API.

Relay и сетевые посредники всё ещё могут наблюдать IP, время, объём и
обращения к очередям. Смешивание трафика, Tor и защита от корреляции пока
не реализованы.

Последовательная отправка сохраняет FIFO при честном relay. Злонамеренный
relay может переставить сообщения за пределы окна skipped keys Olm или
поставить ошибочный конверт первым в очереди. Клиент не подтверждает такой
конверт, поэтому он может остановить получение следующих сообщений.
Защита содержимого не гарантирует доступность. Политика восстановления
после подобных ошибок — отдельная работа.

Проверки выполнены в Linux с настоящими loopback TCP-соединениями.
Пользователь подтвердил работу сетевого этапа на Windows, затем сообщил
об отсутствии ошибок при проверке DPAPI и `windows_profile`.
Пользователь также сообщил об успешной проверке архива приглашений на Windows.
Вывод этих локальных запусков не собирался. Позднее пользователь подтвердил
Windows / Android GUI, ручной обмен 0.1.0 и автоматический обмен 0.1.1;
точные границы указаны в [VALIDATION.md](VALIDATION.md).
Новый quick-сценарий 0.2.0, камера, URI и обновление на устройствах ещё
не подтверждены. Отключение питания, злонамеренный rollback, отказы Keystore
и аппаратная защита ключа остаются непроверенными.
