# Билет на создание одной очереди

Обычный клиент создаёт входящую очередь по ограниченному билету relay,
полученному от владельца сервера. Билет позволяет подготовить одну очередь
и не даёт административных прав. Он отделён от Offer/Reply для контакта:
сначала создаётся очередь, затем её write capability попадает в приглашение.

## Выдача владельцем relay

Команду выполняют там, где доступна постоянная SQLite база relay.
Из корня проекта укажите именно файл, который использует работающий сервер:

~~~powershell
$env:RELAY_DATABASE = "C:\путь\к\данным\relay.sqlite"
cargo run -p messenger-relay --example queue_ticket --locked
~~~

`RELAY_DATABASE` обязателен; пустой путь и `:memory:` отклоняются.
Укажите существующую серверную базу. Другая база выдаст билет, который
работающий relay не узнает. Это локальная операторская команда,
ей не нужен admin-токен по HTTP.

При успехе программа один раз выводит только секрет билета: 64 hex-символа
нижнего регистра. Передайте его выбранному участнику. На relay сохраняется
SHA-256 хеш, а не сам секрет; повторно получить этот секрет из базы нельзя.
Не вставляйте его в публичные логи. Старый обмен Offer/Reply требует двух
входящих очередей и двух отдельных билетов, по одному для каждой стороны.
Новый серверный механизм приглашения позволяет выдать второй билет
автоматически, если владелец явно разрешил такую выдачу; обычный билет
сохраняет прежнее право только на одну очередь.

Срок по умолчанию — 3600 секунд. Его можно изменить перед выдачей:

~~~powershell
$env:RELAY_TICKET_TTL = "7200"
cargo run -p messenger-relay --example queue_ticket --locked
~~~

Допускается от 1 до 86400 секунд. Срок начинает действовать при выдаче,
а не после первого использования. Истечение билета не удаляет уже созданную
очередь и не задаёт срок действия Offer/Reply.

## Обмен с сервером

`POST /v1/queues/redeem` принимает `Authorization: Bearer <ticket>` и строгий
JSON proposal:

~~~json
{"id":"32 lowercase hex characters","read_token":"64 lowercase hex characters","write_token":"64 lowercase hex characters"}
~~~

Это описание полей, а не готовое тело запроса. ID и оба разных токена
выбирает Rust-клиент случайно. Перед HTTP он атомарно сохраняет их вместе
с контактом, артефактом и билетом в зашифрованном локальном состоянии.
После этого сервер создаёт именно предложенную очередь. Ответ —
HTTP `201` и `{ "id": "..." }`, без read/write tokens и без билета.

| Ситуация | Результат |
|---|---|
| Действующий новый билет, свободный ID | Создание очереди и расходование билета одной транзакцией |
| Тот же действующий билет и точный proposal | Снова `201`, тот же ID и та же очередь |
| Использованный билет и изменённый proposal | `409` |
| Неизвестный или истёкший билет | `401` |
| Некорректный proposal при действующем билете | `400` |
| Очередь с этим ID, но другими capabilities | `409` |
| Очередь удалена после расходования этого билета | `404`; повтор не восстанавливает её |
| Исчерпана квота | `429`; новая очередь не создаётся |

Для квоты, записи очереди и расходования билета используется одна
`BEGIN IMMEDIATE` транзакция. Два параллельных разных proposal с одним
билетом не создают две очереди. На relay хранится digest proposal и хеши
capabilities; секретные токены не добавляются в ответ.

## Билет приглашения и ограниченное делегирование

Владелец может отдельно выдать билет для одного приглашения:

~~~powershell
cargo run -p messenger-relay --example queue_ticket --locked -- --invite
~~~

`RELAY_DATABASE` и `RELAY_TICKET_TTL` работают так же, как при обычной выдаче.
Срок по умолчанию для `--invite` — 86400 секунд, для обычного билета —
3600 секунд; для другого срока явно задайте `RELAY_TICKET_TTL`.
Исходный 64-символьный секрет не содержит срок действия:
клиенту нужно выбрать срок приглашения в пределах фактического срока билета.
Старые и обычные билеты при миграции остаются неделегирующими
(`can_invite=0`); новое право получают только билеты, явно выданные через
`--invite` / `Store::issue_invitation_ticket`.

`POST /v1/queues/invite` использует исходный билет в Bearer и принимает:

~~~json
{
  "queue": {
    "id": "32 lowercase hex characters",
    "read_token": "64 lowercase hex characters",
    "write_token": "64 lowercase hex characters"
  },
  "recipient_ticket": "64 lowercase hex characters",
  "expires_at": 1790000000
}
~~~

Это описание полей, не готовый запрос. Клиент случайно выбирает все секреты
и сохраняет точный объект до HTTP. `recipient_ticket` должен отличаться
от исходного билета и обоих токенов очереди. `expires_at` — целые Unix-секунды,
строго позже текущего времени после получения блокировки SQLite, не позже
исходного билета и не более чем через 86400 секунд. Сервер не продлевает и
не корректирует этот срок. Ответ — `201` с `{ "id": "..." }` без секретов.

Одной `BEGIN IMMEDIATE` транзакцией создаются очередь автора и запись
дочернего билета, а исходный билет расходуется с digest всех полей. В
дочерней записи `can_invite=0`: получатель может создать одну очередь через
`/redeem`, но не может выпустить следующий билет. Это разрешение передаётся
внутри приглашения, поэтому получателю не требуется отдельный операторский
билет. Одно приглашение предназначено для одного получателя: первый
успешный `/redeem` связывает дочерний билет с его точным proposal.

| Ситуация `/invite` | Результат |
|---|---|
| Действующий билет приглашения, корректный новый объект | `201`, очередь и дочерний билет созданы атомарно |
| Точный повтор до истечения дочернего билета | Снова `201`; ранее погашенный дочерний билет не сбрасывается |
| Обычный, старый или дочерний билет | `403`; полномочия не расширяются |
| Неизвестный/истёкший исходный билет | `401` |
| Недопустимый объект или срок | `400` |
| Изменение уже связанного объекта, столкновение ID/capabilities или дочернего билета | `409` |
| Удалённая после успеха очередь либо дочерняя запись | `404`; повтор не восстанавливает их |
| Полная квота очередей или билетов | `429`; исходный билет остаётся нерасходованным |

После истечения дочернего билета точный `/invite` не выдаёт его повторно,
даже если исходный билет ещё действителен. Уже созданные очереди живут
независимо от срока билетов. Создание очереди получателя проверяет общую
квоту в момент `/redeem`: место для неё не резервируется при `/invite`.

В relay SQLite не сохраняются явные связи «исходный билет → дочерний билет»
или «билет → очередь», только хеши, digest, срок и флаг полномочий. Это не
скрывает связь от наблюдающего relay: при обработке `/invite` сервер видит
оба разрешения и очередь в одном запросе, а также IP и время обращения.
Секреты нельзя добавлять в access/error-логи или ответы об ошибках.

## Восстановление клиента

Высокоуровневые методы `create_invitation_with_ticket` и
`accept_invitation_with_ticket` сначала сохраняют точные параметры,
затем погашают билет. Для принятия Offer проверка полного артефакта и
независимого отпечатка предшествует сохранению и HTTP. Ошибка HTTP оставляет
контакт с ожидающим заданием, а не создаёт новый комплект очередей.

`provision_queue(contact, None)` повторяет сохранённый proposal с прежним
билетом. Если сервер выполнил запрос, но ответ потерялся, точный повтор
подтверждает ту же очередь до истечения билета. Успех удаляет локальное
ожидающее задание и разрешает экспорт Offer/Reply.

После истечения нужен новый билет: `provision_queue(contact, Some(ticket))`.
Новый билет сохраняется до HTTP; ID и capabilities остаются прежними.
Если очередь уже создана, совпадающие capabilities позволяют подтвердить
её и расходовать новый билет. Если её нет, новый билет может создать её.
Старый израсходованный билет удалённую очередь не восстанавливает.

Пока задание ожидает подтверждения, экспорт, завершение Offer и синхронизация
этого контакта отклоняются. Desktop actor также запрещает добавлять сообщения.
В UI контакт виден как «Очередь ждёт создания» и предлагает повторную попытку.
Низкоуровневые API с готовым `ReceiveQueue` остаются доступны для тестов
и вызывающего кода, который уже получил очередь другим способом.

## Квоты и границы

На relay допускается до 1024 неистёкших билетов, включая уже израсходованные,
и до 256 очередей. Израсходованный билет хранится до срока, чтобы точный
повтор оставался возможен. Просроченные записи удаляются при обслуживании
или выдаче следующего билета. Отзыва отдельного билета и UI для владельца
сервера пока нет.

Билет не является аккаунтом или глобальным ID пользователя. Relay всё ещё
видит IP, время погашения и обращения к очередям. Любой обладатель билета
может успеть использовать его первым. Проверка личности собеседника остаётся
за независимой проверкой отпечатков [приглашений](INVITATIONS.md).
Для внешней сети требуется HTTPS. Развёртывание на VPS этим этапом не выполнялось.
