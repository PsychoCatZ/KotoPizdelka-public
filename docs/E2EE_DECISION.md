# E2EE: решение для первого эксперимента

Дата: 2026-10-02. Статус: учебный прототип, не выпуск для реальной переписки.

## Выбор

Для личного диалога используем `vodozemac 0.11.1`, реализацию Olm / Double
Ratchet на Rust, Apache-2.0, минимальный Rust 1.89. Версия зафиксирована точно
в manifest и Cargo.lock. Legacy compatibility и экспериментальные features
отключены. Для групп позднее отдельно рассмотрим OpenMLS.

Сравнение:

| Вариант | Вывод |
|---|---|
| vodozemac | Высокоуровневые личные сессии, pure Rust; подходит для текущего эксперимента |
| libsignal | Сильный кандидат, но авторы не поддерживают использование вне Signal, API могут меняться; AGPLv3 |
| OpenMLS | Стандарт RFC 9420; подходит для групп, требует отдельного lifecycle эпох, commits, credentials и persistence |

## Конфигурация Olm

Выбран стабильный `SessionConfig::version_1()`. Его HMAC усечён до **8 байт**.
Это 64-битный тег аутентификации, не 256-битная стойкость к подделке сообщения.
У upstream конфигурация v2 с полным MAC находится за feature
`experimental-session-config`. Мы не включаем её автоматически и не делаем
вид, что v1 соответствует всем требованиям будущего выпуска.

До реального использования нужен отдельный пересмотр выбора протокола,
MAC-профиля, ограничений частоты попыток и поддержки обновлений. Самостоятельно
менять ratchet или дописывать к протоколу MAC не будем. Постквантовая защита
этой интеграцией не обеспечивается.

## Идентификация контакта

На каждый контакт создаётся отдельный `Account`. Общий публичный ключ
пользователя не распространяется между контактами. Публичный bootstrap bundle
содержит версию профиля, Curve25519 identity key и единственный одноразовый key.
SHA-256 fingerprint связывает все поля bundle; это отпечаток ключевого bundle,
а не долгоживущий глобальный идентификатор пользователя.

Обе стороны заранее аутентифицируют bundle через независимый доверенный канал.
В локальном примере оба объекта находятся в одном процессе и поэтому считаются
доверенными. Сравнение bundle с fingerprint, полученным рядом с ним от
непроверенного сервера, **не защищает от MITM**. [Обмен приглашениями](INVITATIONS.md)
и первый [Windows UI](DESKTOP.md) дополнительно проверяют полный артефакт,
включая write endpoint и привязку Reply к Offer. Независимый доверенный
отпечаток требуется обеим сторонам. QR-коды пока не реализованы.

Одна сторона явно инициирует сессию. Одновременное создание двух сессий,
восстановление контакта с новыми ключами и ротация bootstrap keys ещё не описаны.

## Конверт и состояние

Форма `{id,payload}` совместима с relay: payload — base64 JSON Olm-сообщения.
ID продублирован внутри зашифрованного plaintext и проверяется после расшифровки.
На существующей сессии PreKey должен соответствовать её session keys.
Обработка выполняется на временной копии state, принятие — после всех проверок.
Подмена ID, недопустимый plaintext или неверный MAC не расходуют основной state.

Snapshot включает account, session и оба bindings в одном AEAD-конверте.
Используется готовый XChaCha20Poly1305 RustCrypto, случайные 32-байтный ключ и
24-байтный nonce из OS RNG, фиксированный AAD с версией формата. Ключ не пароль.
В клиенте он должен быть защищён средствами ОС и не храниться открытым текстом
рядом со snapshot. Для Windows подключён DPAPI с opaque sidecar;
подробности в [STORAGE_KEYS.md](STORAGE_KEYS.md).
Шифрование snapshot не защищает от возврата к старому валидному
состоянию. Атомарные транзакции теперь реализованы в `messenger-store`;
защита от злонамеренного rollback требует отдельной модели хранения и пока не обещается.

После encrypt клиент обязан атомарно сохранять новое состояние и точный
конверт в outbox **до** отправки. Повтор отправки использует этот же конверт.
После decrypt он атомарно сохраняет состояние и inbox **до** подтверждения relay.
Это выполняют `ClientStore::enqueue` и `ClientStore::accept`; отдельный
in-memory API core остаётся низкоуровневым и не выполняет запись на диск.
Store получает ключ от вызывающего кода; Windows-клиент может раскрывать его
через DPAPI. Системное хранение Android ещё не подключено.
Схема и ограничения приведены в [CLIENT_STORE.md](CLIENT_STORE.md).

Перестановка небольшого числа сообщений поддерживается Olm: в проверенной
версии остаётся до 40 skipped keys на chain и до 5 receiving chains;
принимаемый разрыв ограничен 2000 шагами. Transport pacing и длительные разрывы требуют
отдельной интеграции. Публичные bootstrap keys в PreKey можно наблюдать на relay;
они ограничены контактом, но внутри контакта остаются связываемыми.

## Проверки и ограничения

Нужны обмен в обе стороны, чужой отправитель, подмена ciphertext и ID,
повтор сообщения, перестановка, восстановление bootstrap и established state,
неверный ключ хранения, повреждённый snapshot и пределы размеров.

Upstream сообщает об аудите Least Authority; он не является аудитом нашей
оболочки и не означает, что текущая версия или приложение полностью проверены.
Объём текста ограничен 24 KiB UTF-8, wire payload — 64 KiB. JSON escaping может
увеличить размер; текст внутри первого предела иногда превышает второй.
Core прошёл `cargo check --lib` для Android ARM64 и Windows MSVC, тесты и
пример выполнены в Linux. Пользователь также подтвердил работу сетевого архива
на Windows, затем сообщил об отсутствии ошибок при проверке DPAPI и
windows_profile. Вывод этих локальных команд отдельно не предоставлялся.
Новый обмен [приглашениями](INVITATIONS.md) дополнительно связывает bundle,
роль и write endpoint проверяемым полным отпечатком; пользователь также сообщил
об успешной проверке предыдущего архива приглашений на Windows.
Первый Windows UI реализован, но его нативный запуск ещё требует проверки.
Запуск Android и его интерфейс ещё требуют реализации и проверки.
